## What the server is

- Code: `mcp_server/` on `main` (merged in PR #41). One Model Context
  Protocol server over stdio (JSON-RPC 2.0, newline delimited).
- Entry point: `python3 -m mcp_server`, run from the repository root; the
  generated manifest starts it as `python -m mcp_server`.
- One tool: `recall_check`. Arguments: `product`, `exact_name`, `near`
  (product form, CPSC SaferProducts) or `make`, `model`, `year`, `exclude`
  (vehicle form, NHTSA recalls). Full schema: the server's own `tools/list`
  response, reproduced in [`LISTING.md`](LISTING.md).
- Output: the recall check as Markdown in the repo's fixed evidence format;
  a failed fetch or bad request is a tool error (`isError: true`), never an
  empty result.

## Prerequisites the host must meet (known from the core)

1. Python 3.10 or later. The generated manifest declares `runtime: python`
   without a version; the coordinator's reading of the publish page names
   3.11 or 3.12 as the server runtimes, either of which satisfies the core.
2. `curl` on PATH. The CPSC fetcher captures responses with the system curl
   executable (`tools/README.md`). Whether the MCPize runtime image has
   curl is not known from this repo; if it does not, every product form
   call returns the fail closed tool error "curl unavailable or timed out"
   and the listing must say the product form is unavailable there.
3. Outbound HTTPS to `www.saferproducts.gov` and `api.nhtsa.gov`. The
   server fetches live on every call and caches nothing.
4. No Python packages. No API keys. No secrets of any kind.
5. One optional environment value: `PAYOUT_WALLET_ADDRESS`, the EVM address
   (0x plus 40 hex digits) that receives USDC per call, set in the host's
   environment, never in a file in this repo. The server refuses to start on
   a malformed value and runs without one when it is unset. On MCPize the
   payout recipient is the `recipient` in the manifest's pricing block
   (above), so this value is informational there and may stay unset.
6. The repository checkout as working directory, since the server imports
   `api/recall_api.py` and `tools/` as library code. The generated manifest
   runs from the repository root.

## Tools added to the core after deployment (issue #67)

The core on `main` now lists three tools: `recall_check`, and from issue
#67 `carrier_check` (FMCSA carrier vetting via `tools/fmcsa_carrier.py`)
and `litigation_screen` (CourtListener RECAP docket screen via

What that means for the deployment, stated plainly:

- **Auto deploy stays off.** Merging the two tools to `main` changes the
  code in this repository and nothing on MCPize. Putting the new tools live
  on MCPize is a deliberate later step, taken by the owner from the MCPize
  side when they choose, not part of issue #67 and not part of any merge.
- **No pricing change.** The pricing block in the root `mcpize.yaml` names
  one priced tool, `recall_check`, and issue #67 does not touch that file.
  The two new tools carry no price in the manifest and no payout sentence
  in their tool descriptions. Whether and how to price them is the owner's
  decision, recorded in the manifest or the dashboard when it is made.
- **Listing copy unchanged.** `LISTING.md` describes the live server's one
  priced tool and stays as it is until the new tools are deployed.
- **Prerequisites the new tools add**, for the day they go live: outbound
  HTTPS to `data.transportation.gov`, `safer.fmcsa.dot.gov`,
  `li-public.fmcsa.dot.gov` and `www.courtlistener.com`; optionally
  `COURTLISTENER_TOKEN` in the host environment (lifts CourtListener's
  anonymous rate limit; read at call time, never printed, never in a file
  in this repo). Whether the MCPize runtime reaches those hosts is not
  known from this repo and is a check for the go-live step.
